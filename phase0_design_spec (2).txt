========================================================================

  3. 過去の約定履歴CSV（https://api.coin.z.com/data/trades/）およびPublic APIが無料公開されている。
- 制約・未確認事項：
  1. 公式のテストネット／Sandbox環境の有無は、今回確認した公式資料からは確定できないため「未確認」として扱う。ペーパートレードはローカルの擬似執行（Public WebSocket＋保守的約定モデル）で構築する。

[第二候補] 米国株・ETF（Alpaca Paper Trading API：SPY等）
- 用途の限定：

3. 初期戦略の再現可能な厳密仕様（F0-Strategy-002）
========================================================================

旧戦略案（F0-Strategy-001：SMA20クロス等）がある場合は比較用ベースラインまたは別IDとして履歴保持し、黙って上書きしない。本仕様では新ID「F0-Strategy-002」として以下の通り完全に定義する。なお、ATRはエントリー条件ではなくストップ幅の決定に用いるため、戦略名称を実態に合わせて改称した。

戦略名：ドンチャン・ブレイクアウト＋ATRベースストップ戦略（F0-Strategy-002）
- 対象市場・形態：BTC/JPY 現物（ロングのみ・レバレッジなし・最大同時保有1ポジション・利確TP条件なし）
- 基準時刻・足確定：UTC 1時間足（確定足のみ参照し、未確定足は使用しない）

(1) エントリー条件と執行方式
- ブレイクアウト判定（t本目の1時間足確定時点で判定）：
  Close_t > max(High_{t-N}, High_{t-N+1}, ..., High_{t-1})
  ※現在の足 t の高値は参照期間に含めない。
- 探索期間 N（事前登録）：{20, 24, 36, 48} の4通り。
- エントリー執行：条件成立の次足（t+1）始値基準の成行買いモデル（後述の約定モデルによりスプレッド・スリッページを加味して約定価格を決定）。指値エントリー案は執行特性が異なるため別戦略IDとする。

(2) ATR(14)およびTrue Rangeの定義
- True Range：TR_u = max(High_u - Low_u, |High_u - Close_{u-1}|, |Low_u - Close_{u-1}|)
- ATR(14)：Wilder平滑化方式（初期14本は単純平均、以降 ATR_u = (ATR_{u-1} * 13 + TR_u) / 14）。
- ストップ係数 k（事前登録）：{2.0, 2.5, 3.0} の3通り（N×k 計12通りを事前登録上限とする）。

(3) ストップ処理・72時間決済の厳密な評価順序（先読み完全排除）
初期ストップはエントリー時に Stop_0 = EntryPrice - k * ATR_t として設定する。保有中の足 u における処理は必ず次の順序で実行する：
  Step 1（適用）：足 u の開始時点では、前足 u-1 確定時に決定していた Stop_{u-1} のみを適用する（エントリー直後の足 t+1 では Stop_0 を適用）。
  Step 2（ストップ到達判定）：足 u で Low_u <= Stop_{u-1} となったか判定する。
    - ギャップダウン（飛び越え）約定：Open_u < Stop_{u-1} で始まった場合、Stop_{u-1} ではなく Open_u を基準に売り約定モデル（スプレッド・スリッページ控除）で決済する。
    - 通常到達：Open_u >= Stop_{u-1} かつ Low_u <= Stop_{u-1} の場合、Stop_{u-1} を基準に売り約定モデルで決済する。
    - エントリー足（t+1）の同足内ストップ：Open_{t+1} でエントリー約定後、Low_{t+1} <= Stop_0 の場合は同足内でストップ決済されたものとして保守的に処理する。
  Step 3（72時間タイムストップ）：Step 2で決済されずポジションが残っている場合、エントリー足 t+1 から数えて72本目の足（t+72）が確定した時点でタイムストップを発動し、次足 t+73 の始値を基準に成行売り約定モデルで決済する。
  Step 4（ストップ更新）：Step 2・3のいずれも未発動でポジションが残っている場合のみ、足 u の確定終値 Close_u と ATR_u を用いて Stop_u = max(Stop_{u-1}, Close_u - k * ATR_u) を計算する（上方のみ更新）。
  Step 5（次足適用）：更新された Stop_u は次の足 u+1 から適用する。
- 再エントリー許可：ストップ決済またはタイムストップ決済が発生した足では新規エントリーを行わず、次の確定足から通常のブレイクアウト判定を再開する。

(4) パラメータ選択基準と検証回数制限・反証条件
- Validation選択基準：全12通りのうち、Validation期間で最低取引回数（例：30回以上）を満たす候補の中から、全費用控除後Net Expectancyのブロックブートストラップ下側信頼限界が最大の組合せを1つ選択する（同値の場合は N が大きく k が大きい保守側を優先）。
- 閲覧・検証回数制限：OOSは事前登録設定の検証用とし、最終Holdoutの実行は原則1回限りとする（結果を見て戦略・パラメータを変更した場合、そのHoldoutは消費済みとし再利用禁止）。
- 反証条件：往復Taker手数料＋保守的スリッページ控除後のOOS Net Expectancyが0以下、コスト2倍で期待値マイナス、または特定1〜2回の急騰のみに依存する場合は即座に棄却する。

4. バックテスト約定モデルと数量計算式（P0確定仕様）
========================================================================

(1) バックテスト約定価格・スプレッド・スリッページモデル
GMOコインの過去約定履歴CSV（https://api.coin.z.com/data/trades/）のみでは過去の板厚や最良気配を完全復元できないため、単純な足始値（Open）での約定を禁止し、以下の保守的モデルを適用する：
- 成行買い約定価格（買い気配側基準）：
  ExecBuyPrice = RefPrice * (1 + HalfSpread_est + Slippage_est)
- 成行売り約定価格（売り気配側基準）：
  ExecSellPrice = RefPrice * (1 - HalfSpread_est - Slippage_est)
  ※RefPrice はエントリー・タイムストップ時は次足 Open、ストップ時は Stop 価格（飛び越え時は Open_u）。
  ※過去の板データがない期間では、HalfSpread_est（保守的初期検証値 0.03% 等）および Slippage_est（保守的初期検証値 0.02% 等）を設定し、ストレステストで2倍・3倍を検証する。
- 二重控除の禁止：スプレッドおよびスリッページは約定価格（ExecBuyPrice / ExecSellPrice）に直接織り込むため、損益計算式で同じコストを再度差し引かない。損益計算では別途、取引手数料（Fee = ExecPrice * Qty * TakerFeeRate、GMOコインBTC現物は0.05%）のみを差し引く。
- Paper Tradingでの検証：ライブ環境ではPublic API/WebSocketから板（OrderBook）・Ticker・約定データを継続保存し、モデル想定値と実測値の乖離を検証する。

(2) ポジション数量とGapBufferの計算式（すべてDecimal演算）
1. リスク予算：
   RiskBudget = Equity * RiskRate
2. 1単位あたり想定最大損失（GapBuffer含む）：
   LossPerUnit = (EntryPrice_est - StopPrice_est) + EntryFeePerUnit + ExitFeePerUnit + SlippagePerUnit + GapBufferPerUnit
   ※ここで EntryPrice_est は上記約定モデル込みの買値、GapBufferPerUnit は急落時のストップ飛び越えリスクを吸収するバッファ（例：GapBufferPerUnit = g * ATR_t、初期検証値 g=0.5 として、g ∈ {0.0, 0.5, 1.0} でストレステストを実施）。
3. 理論数量：
   QtyRaw = RiskBudget / LossPerUnit（LossPerUnit <= 0 または NaN の場合は Fail-Closed で拒否）
4. 制約・丸め適用（順序厳守）：
   - 利用可能JPY残高上限：QtyCashCap = AvailableJPY / (EntryPrice_est * (1 + EntryFeeRate) * CashBufferRatio)
     ※GMOコイン取引ルール等の余力バッファ（例：1.1）を考慮。
   - 取引所・エクスポージャー上限：QtyMaxCap = min(5.0 BTC, MaxExposureQty)
   - 上限適用：QtyCapped = min(QtyRaw, QtyCashCap, QtyMaxCap)
   - 注文単位切り下げ：QtyFinal = floor_to_step(QtyCapped, step=0.00001 BTC)
     ※最小注文数量（0.00001 BTC）に合わせるための切り上げは絶対禁止。
   - 最小注文数量チェック：QtyFinal < 0.00001 BTC の場合は取引見送り（SKIP）。
   - 最終検算：QtyFinal * LossPerUnit <= RiskBudget を再確認する。

6. 5 Plane アーキテクチャと LLM の権限境界
========================================================================

1. Research Plane（研究領域）：データ収集・品質検証、仮説探索、IS/Validationバックテスト、LLMによる要約・仮説提案。
2. Evaluator Plane（独立評価領域）：固定されたMetrics Registry定義による再計算、整合性検査、OOSおよび隔離された読み取り専用Holdoutでの採用/保留/棄却判定。Research側から書換不可。
3. Trading Plane（ペーパートレード領域）：ライブデータ検査、承認済み戦略実行、SignalIntent生成、Fail-Closed Risk Gate、単一注文主体への指示、口座照合。初期MVPはペーパートレード専用。
4. Transparency Plane（透明性・監査領域）：読み取り専用の監査ログ、Event Ledger閲覧、Experiment/Evaluation結果・Strategy Healthレポート出力。発注・設定変更権限なし。
5. Operations Plane（運用・監視・復旧領域）：死活監視、リソース/APIレート/費用監視、日次暗号化バックアップと復元訓練、Bot外部キルスイッチ運用。

[LLMの権限境界の明文化]
- LLMは注文APIへアクセスできない。
- LLMはRisk Gateの判断を上書きできない。
- LLMはリスク設定・承認済み戦略・Evaluator基準を直接変更できない。
- LLMの提案は人間による承認または決定論的な検証処理を経なければ採用されない。

7. 直交する状態機械（システム4軸 ＋ 注文11状態と厳密な遷移ルール）
========================================================================

(1) システム状態（相互に直交する4軸＋健全性フラグ）
- ExecutionMode：RESEARCH / BACKTEST / PAPER（本番LIVEは初期MVPで到達不能）
- RuntimeState：INITIALIZING -> DATA_SYNCING -> RECONCILING -> READY -> RUNNING / PAUSED / ERROR
- RiskState：NORMAL / COOLING_DOWN / DAILY_STOPPED / WEEKLY_STOPPED / DRAWDOWN_STOPPED / EMERGENCY_STOPPED / MANUAL_REVIEW_REQUIRED（複数競合時は最厳格状態を優先）
- PositionState：FLAT / OPEN / PARTIALLY_CLOSED / UNKNOWN
- 健全性フラグ：HEALTHY / DATA_ERROR / API_ERROR / EXECUTION_UNKNOWN

(2) 注文状態機械（11状態）と ERROR / UNKNOWN の厳密な区別
状態一覧：CREATED, SUBMITTING, ACKNOWLEDGED, PARTIALLY_FILLED, FILLED, CANCEL_PENDING, CANCELED, REJECTED, UNKNOWN, EXPIRED, ERROR

[ERROR と UNKNOWN の定義]
- ERROR：注文送信「前」のローカル検証失敗・署名構築失敗・ネットワーク未到達が確実なエラーのみ。予約は即座に解放可能。
- UNKNOWN：注文送信「後」のタイムアウト・応答消失・HTTP 5xx等で、取引所が注文を受理したか確定できない状態。外部口座・注文一覧を照合して最終状態が確定するまで予約を絶対解放せず、盲目的な再送も禁止。

[許可される状態遷移]
- CREATED -> SUBMITTING | ERROR
- SUBMITTING -> ACKNOWLEDGED | FILLED | REJECTED | UNKNOWN | ERROR（送信後不明は必ずUNKNOWN）
- ACKNOWLEDGED -> PARTIALLY_FILLED | FILLED | CANCEL_PENDING | CANCELED | EXPIRED | UNKNOWN
- PARTIALLY_FILLED -> PARTIALLY_FILLED | FILLED | CANCEL_PENDING | CANCELED | EXPIRED | UNKNOWN
  ※PARTIALLY_FILLEDからCANCELED/EXPIREDに遷移した場合、約定済み数量（filled_qty）は実ポジションリスクへ移行・保持し、未約定残数量（remaining_qty）の予約のみを解放する。
- CANCEL_PENDING -> CANCELED | PARTIALLY_FILLED | FILLED | UNKNOWN
  ※取消要求中に約定通知が届いた場合は約定を優先反映する。
- UNKNOWN -> ACKNOWLEDGED | PARTIALLY_FILLED | FILLED | CANCELED | REJECTED | EXPIRED（外部照合結果によってのみ遷移）
- EXPIRED：取引所側の価格制限（GMOコインの「約定価格平均値±20%範囲外でのTaker失効」等）または有効期限切れにより失効した場合に遷移。
- 終端状態：FILLED, CANCELED, REJECTED, EXPIRED, ERROR（終端状態からの逆戻りは禁止）。

8. Risk Gate・リスク予約・Emergency Reduction・損失定義
========================================================================

- 損失上限の計算定義（数値候補：1トレード0.1〜0.25%、日次-1.0%、週次-2.5%、DD -5%警告/-8%停止、3連敗は未承認・比較用仮定値）：
  日次リセットはUTC 00:00、週次リセットは月曜UTC 00:00。実現損益＋未実現損益（Mark評価）＋手数料＋スリッページ＋保有コストを含め、入出金・振替はキャッシュフロー調整としてDD（HWM基準）から厳密分離する。オープンリスクは実建玉＋未約定＋UNKNOWN＋未解放予約の合算で検査する。
- リスク予約ライフサイクルとDB競合制御：
  拒否(REJECTED/ERROR)＝即解放 ／ 取消確定(CANCELED)＝残数量照合後に解放 ／ 全量約定(FILLED)＝実ポジション移行 ／ 部分約定＝約定分移行・残数量維持 ／ UNKNOWN＝照合まで維持 ／ 期限切れ(EXPIRED)＝外部状態確認後に解放。
  SQLiteでは `BEGIN IMMEDIATE`、PostgreSQLでは `SERIALIZABLE` または行ロック（`SELECT ... FOR UPDATE`）＋楽観ロック用バージョン番号＋一意制約 `UNIQUE(account_id, instrument, client_order_id)` で競合・二重予約を防止する。
- Emergency Reduction Executor：
  通常Risk Gate停止時は、独立した「事前承認済みの決定論的Emergency Policyモジュール」が `EmergencyReductionAuthorization`（1回限り消費・有効期限付）を発行する。BTC/JPY現物では `reduceOnly` に依存できないため、外部口座APIから取得した現物の売却可能残高（未約定売り注文でロック済みの数量を除外した `available_balance`）を照合し、`order_qty <= min(tracked_position_qty, available_balance)` の売却のみ許可する（反転・空売り禁止）。

- 保存分離（軽量Python自作コア）：

  `schema_version`, `event_id`, `created_at` (UTC), `event_time` (市場発生時刻), `received_at` (受信時刻), `available_at` (戦略利用可能時刻), `source`, `source_event_id`, `correlation_id`, `normalization_version`, `raw_data_ref`, `quality_state`。価格・数量は `Decimal` 型を使用。
