3. 初期戦略の再現可能な厳密仕様（F0-Strategy-002）
========================================================================

旧戦略案（F0-Strategy-001：SMA20クロス等）がある場合は比較用ベースラインまたは別IDとして履歴保持し、黙って上書きしない。本仕様では既存ID「F0-Strategy-002」を維持し、新しい戦略IDを追加しない。

戦略名：ドンチャン・ブレイクアウト＋ATRベースストップ戦略（F0-Strategy-002）
- 対象市場・形態：BTC/JPY 現物（ロングのみ・レバレッジなし・最大同時保有1ポジション・利確TP条件なし）
- 基準時刻・足確定：UTC 1時間足（確定足のみ参照し、未確定足は使用しない）

(1) エントリー条件・使用データ限定・遅延考慮の執行タイミング
- ブレイクアウト判定（t本目の1時間足確定時点で判定）：
  Close_t > max(High_{t-N}, High_{t-N+1}, ..., High_{t-1})
  ※現在の足 t の高値は参照期間に含めない。
- 探索期間 N（事前登録）：{20, 24, 36, 48} の4通り。
- 使用データの厳格限定（OHLCVのみ期間の除外）：
  約定履歴CSV（ティック単位）が存在せず1時間足OHLCVのみしか存在しない期間は、**最終的な戦略評価（Validation / OOS / Holdout）には使用しない**。
- 遅延を考慮したエントリー基準価格：
  `available_at + order_latency_est` より後に到来する約定履歴CSV上の最初の約定価格を `RefPrice` とする（遅延シナリオ：`order_latency_est ∈ {1s, 5s, 30s, 60s}`）。指値エントリー案は執行特性が異なるため別戦略IDとする。

(2) ATR(14)およびTrue Rangeの定義
- True Range：TR_u = max(High_u - Low_u, |High_u - Close_{u-1}|, |Low_u - Close_{u-1}|)
- ATR(14)：Wilder平滑化方式（初期14本は単純平均、以降 ATR_u = (ATR_{u-1} * 13 + TR_u) / 14）。
- ストップ係数 k（事前登録）：{2.0, 2.5, 3.0} の3通り（N×k 計12通りを事前登録上限とする）。

(3) ストップ処理・72時間決済の厳密な評価順序（先読み・時間矛盾の完全排除）
初期ストップはエントリー約定時に `Stop_0 = Position.avg_entry_price - k * ATR_t` として設定する。

[エントリー足（t+1）におけるストップ判定の優先順位]
  1. ティックデータ（約定履歴CSV）がある場合：実際の約定時刻（`FirstFillTime`）**以降**に記録された約定価格のみを対象として `price <= Stop_0` を判定する。
  2. ティックデータがなく1時間足OHLCVのみの場合（補助確認時のみ）：エントリー足（t+1）のストップ判定は**保留**し、次の完全な足（t+2）の開始時点から `Stop_0` の到達判定を開始する。
  3. 急落リスクの検証：エントリー直後の急落リスクは別途ストレステストで検証・報告する。

[保有中の足 u における評価順序]
  Step 1（適用）：足 u の開始時点では、前足 u-1 確定時に決定していた `Stop_{u-1}` のみを適用する。
  Step 2（ストップ到達判定）：足 u（または約定後ティック）で `Low <= Stop_{u-1}` となったか判定する。
    - ギャップダウン（飛び越え）約定：`Open_u < Stop_{u-1}` で始まった場合、`Stop_{u-1}` ではなく `Open_u`（または利用可能最初の約定価格）を基準に売り約定モデルで決済する。
    - 通常到達：`Open_u >= Stop_{u-1}` かつ `Low_u <= Stop_{u-1}` の場合、`Stop_{u-1}` を基準に売り約定モデルで決済する。
  Step 3（72時間タイムストップ）：
    `TimeStopAt = FirstFillTime + 72h` と定義する。Step 2で決済されずポジションが残っている場合、`TimeStopAt` 以降に利用可能となった最初の価格（`available_at >= TimeStopAt + order_latency_est`）を基準に成行売り（FAK）約定モデルで決済する。
  Step 4（ストップ更新）：Step 2・3のいずれも未発動でポジションが残っている場合のみ、足 u の確定終値 `Close_u` と `ATR_u` を用いて `Stop_u = max(Stop_{u-1}, Close_u - k * ATR_u)` を計算する（上方のみ更新）。
  Step 5（次足適用）：更新された `Stop_u` は次の足 u+1 から適用する。
- 再エントリー許可：決済が発生した足では新規エントリーを行わず、次の確定足から通常のブレイクアウト判定を再開する。

(4) Validationの統計的選択基準・ブロック長感度分析・選択バイアス対策
- 評価指標の固定：
  **全費用控除後の1トレード当たり Net Expectancy（R倍数を主指標とし、JPY純損益も併記）**。
- ブロックブートストラップ仕様（事前登録）：
  - 手法：**定常ブートストラップ（Stationary Bootstrap）**。
  - 平均ブロック長：主基準 **`L = 5` トレード** を事前登録する。Validation閲覧後の事後変更・事後選択は禁止し、頑健性確認のため事前登録した感度分析（**`L ∈ {3, 5, 10}`**）の結果を最終評価レポートに必ず併記する。
  - 信頼水準・反復回数・乱数：`95%`、反復回数 `B >= 2,000`、乱数シード固定。
- 12通りの選択バイアス対策：
  1. 最低取引回数（30回以上を足切り基準とするが、30回のみで十分な統計的検出力を保証しない）を満たす候補から下側信頼限界最大の1案を「検証候補」として絞り込む（CIがゼロをまたぐ場合は採用不可）。同値時は N 大・k 大の保守側を優先。
  2. Validationは候補絞り込みのみとし、多重比較補正（Holm/Bonferroni等）の診断値を併記する。
  3. **最終採否は、Validationで固定した1設定のみを独立したOOSおよび1回限りの最終Holdoutへ持ち込んで再現性を確認すること**で判定する（Holdout閲覧後の変更は絶対禁止）。

4. バックテスト約定モデル・重複排除・部分約定リスク配分式（P0確定仕様）
========================================================================

(1) 過去データ用FAK部分約定モデルとPaper Trading用モデルの分離
GMOコイン現物の成行注文は FAK（一部約定後、未執行残数量は即座に失効）であるため、両モデルを完全に分離し、**過去データ用近似モデルの結果と実板情報を使ったPaper Tradingの結果を混同しない**。

[過去データ用：数量上限の近似モデル ＋ サイズ連動価格モデル（バックテスト専用）]
- 位置づけ：`FillableCap = alpha * recent_volume_5m` は**実際の板厚や約定可能数量を再現するモデルではなく、過去データにおいて過大な数量を約定させないための保守的な数量上限の近似モデル**である。
- 出来高集計・参加率・欠損時：`recent_volume_5m`（直前300秒間の約定履歴CSV合計BTC数量）、初期仮定値 `alpha = 0.05`（ストレステスト `{0.01, 0.03, 0.05, 0.10}`）。欠損・品質不良・`0` 時は Fail-Closed（約定不可・SKIP）。
- 約定数量：`filled_qty = floor_to_step(min(order_qty, FillableCap), step=0.00001 BTC)`（`0.00001` 未満はSKIP、残数量はFAK失効）。
- 約定価格モデル（サイズ連動市場インパクトの近似）：
  `ImpactSlippage = Slippage_est * (1 + beta * (filled_qty / FillableCap))`
  ※本式はサイズに応じた保守的ペナルティの**近似モデルであり、実際の市場インパクト（板の弾力性等）を忠実に再現するものではない**。Paper Tradingの実板・実約定乖離データで将来校正し、バックテスト報告時は近似モデルの限界を必ず明記する。
  ※`HalfSpread_est = 0.03%`、`Slippage_est = 0.02%`、`beta = 1.0`、`GapBuffer = 0.5 * ATR_t` は実測値ではなく**設計上の初期仮定値**とし、2倍・3倍のストレステストを実施する。
  - 成行買い：`ExecBuyPrice = RefPrice * (1 + HalfSpread_est + ImpactSlippage)`
  - 成行売り：`ExecSellPrice = RefPrice * (1 - HalfSpread_est - ImpactSlippage)`

[Paper Trading用：OrderBookモデル（ライブ模擬執行専用）]
- 実際のOrderBookスナップショット（Public API/WebSocket）から各価格帯の利用可能数量を取得し、注文送信時点の板を消費して加重平均約定価格・約定数量・FAK残数量失効を算出する。

(2) 約定イベントの重複排除・時間的整合性・部分約定リスク配分式
- **約定イベントの重複排除キーと冪等処理**：
  取引所が発行する一意の約定ID（`source_execution_id`）を必須保存し、DBスキーマ上で複合一意制約 **`UNIQUE(exchange, account_id, instrument, source_execution_id)`** を強制する。
  同一の約定IDが再受信された場合、システムはべき等に処理し、**ポジション数量、加重平均取得価格、手数料、リスク予約を一切変更せず**、重複受信を検出した事実（元 `event_id` と再受信 `received_at`）を監査ログへ記録する。
- 単一ポジション管理と遡及変更の禁止：
  初期MVP（最大1ポジション）では「加重平均取得価格による単一ポジション管理」を採用する。約定イベントの統合は `event_time` 順で決定論的に行うが、ストップ適用履歴は各判定時点の `received_at` スナップショットとして不変記録し、遅延・逆順到着したイベントによる再計算は**過去の実行済みストップ判定を遡って書き換えず、現在以降（`received_at` 以降の次回評価タイミング）の状態および `Stop` 価格にのみ反映**する。
- **部分約定時の予約リスク配分式（すべてDecimal演算・DBトランザクション内原子的更新）**：
  発注前に確保する初期予約：
  - `InitialOrderQty = QtyFinal`
  - `InitialReservedPerUnit = LossPerUnit`（`EntryExecPrice - StopExitExecPrice + EntryFeePerUnit + ExitFeePerUnit + GapBufferPerUnit`）
  - `ReservedRiskForOrder_initial = InitialOrderQty * InitialReservedPerUnit`
  部分約定イベント到着時（累計約定数量 `filled_qty`、未約定残数量 `remaining_qty = InitialOrderQty - filled_qty`）：
  1. **約定済み分の実リスク再計算**：実際の加重平均取得価格 `avg_entry_price` と、それに基づくストップ `Stop_0 = avg_entry_price - k * ATR_t`（売り約定モデル適用後の `ActualStopExitPrice`）、実約定手数料、`GapBufferPerUnit` を用いて算出：
     `ActualPositionRisk = filled_qty * ((avg_entry_price - ActualStopExitPrice) + ActualEntryFeePerUnit + ExitFeePerUnit + GapBufferPerUnit)`
  2. **未約定残分の予約リスク配分**：発注前に確保した単価あたりの予約リスク `InitialReservedPerUnit` を用いて未約定残数量分を保持：
     `RemainingReservedRisk = remaining_qty * InitialReservedPerUnit`
  3. **約定済み分の割当予約超過チェック**：
     当該約定済み数量に割り当てられていた初期予約枠は `AllocatedInitialRiskForFilled = filled_qty * InitialReservedPerUnit`。
     **`ActualPositionRisk > AllocatedInitialRiskForFilled`** または **`(OtherOpenAndReservedRisk + ActualPositionRisk + RemainingReservedRisk) > MaxTotalOpenRisk`** のいずれかを満たした場合は超過を検出し、即座に `RiskState -> MANUAL_REVIEW_REQUIRED` を発動して新規エントリーを停止し人間へ通知する。
  4. **注文の取消・失効・拒否時**：`remaining_qty = 0`（`RemainingReservedRisk = 0`）として未約定分の予約のみを解放し、`ActualPositionRisk` のみを保持する。

(3) 手数料の理論値計算と端数処理（朝6:00返金モデル）
- 理論手数料：`Fee_theoretical = ExecPrice * Qty * FeeRate`（成行買い・売りともにTaker前提 `0.0005` = 0.05%）。
- 実請求・返金処理：Takerは小数点以下切り上げ（`ceil(Fee_theoretical)`）で控除、Makerは切り捨てで計算し、毎営業日（祝日含む）日本時間朝6:00（UTC 21:00）に合算端数の整数部分が返金される処理を会計・残高照合モデルで分離記録する。スプレッド・スリッページは二重控除しない。

(4) 数量計算式（Decimal演算・分離された資金バッファ）
1. 残余リスク予算：
   `BaseRiskBudget = Equity * RiskRate`
   `RiskBudgetBeforeOrder = max(0, min(BaseRiskBudget, MaxTotalOpenRisk - CurrentOpenAndReservedRisk))`（`<= 0` なら拒否）
2. 1単位あたり想定最大損失（二重計上なし）：
   `LossPerUnit = (EntryExecPrice - StopExitExecPrice) + EntryFeePerUnit + ExitFeePerUnit + GapBufferPerUnit`（`<= 0` / `NaN` なら拒否）
3. 理論数量：`QtyRaw = RiskBudgetBeforeOrder / LossPerUnit`
4. 分離された資金上限と制約適用（成行買いTaker前提・Makerマイナス値使用禁止）：
   - `ExchangeMarginFactor`：取引所注文余力倍率（例：GMOコイン成行買余力条件 `1.1`、最新仕様を実装時確認）
   - `EntryFeeRate`：Taker買い手数料率 `0.0005`（正の値）
   - `SystemSafetyBuffer`：システム独自の資金余裕倍率（初期仮定値 `1.05`）
   - `QtyCashCap = AvailableJPY / (EntryExecPrice * (1 + EntryFeeRate) * ExchangeMarginFactor * SystemSafetyBuffer)`
   - `QtyMaxCap = min(5.0 BTC, FillableCap, MaxExposureQty)`
   - `QtyCapped = min(QtyRaw, QtyCashCap, QtyMaxCap)`
   - `QtyFinal = floor_to_step(QtyCapped, step=0.00001 BTC)`（切り上げ絶対禁止、`< 0.00001 BTC` はSKIP）
   - 最終検算：`QtyFinal * LossPerUnit <= RiskBudgetBeforeOrder` を切り下げ後に再計算。手数料通貨（JPY）と数量通貨（BTC）を分離記録する。

[LLMの権限境界]
- LLMは注文APIへアクセスできない。
- LLMはRisk Gateの判断を上書きできない。
- LLMはリスク設定・承認済み戦略・Evaluator基準を直接変更できない。
- LLMの提案は人間による承認または決定論的な検証処理を経なければ採用されない。

7. 直交する状態機械と ERROR / UNKNOWN 境界・GMO API変換規則
========================================================================

(1) システム状態（相互に直交する4軸＋健全性フラグ）
- ExecutionMode：RESEARCH / BACKTEST / PAPER（本番LIVEは初期MVPで到達不能）
- RuntimeState：INITIALIZING -> DATA_SYNCING -> RECONCILING -> READY -> RUNNING / PAUSED / ERROR
- RiskState：NORMAL / COOLING_DOWN / DAILY_STOPPED / WEEKLY_STOPPED / DRAWDOWN_STOPPED / EMERGENCY_STOPPED / MANUAL_REVIEW_REQUIRED
- PositionState：FLAT / OPEN / PARTIALLY_CLOSED / UNKNOWN
- 健全性フラグ：HEALTHY / DATA_ERROR / API_ERROR / EXECUTION_UNKNOWN

(2) 注文状態機械（11状態）と SUBMITTING / ERROR / UNKNOWN の厳密な境界
状態一覧：CREATED, SUBMITTING, ACKNOWLEDGED, PARTIALLY_FILLED, FILLED, CANCEL_PENDING, CANCELED, REJECTED, UNKNOWN, EXPIRED, ERROR
- `SUBMITTING`：注文送信処理（外部APIへのHTTPリクエスト送信）を実行中である状態。
- `ERROR`：送信処理開始「前」（`CREATED` 段階）のローカル検証失敗等のみ（予約即解放可）。
- `UNKNOWN`：送信処理開始「後」（`SUBMITTING` 以降）の通信断・タイムアウト・応答消失・HTTP 5xx等（外部照合完了まで予約維持・盲目的再送禁止）。

[許可される状態遷移（`SUBMITTING -> ERROR` を禁止）]
- `CREATED -> SUBMITTING | ERROR`
- `SUBMITTING -> ACKNOWLEDGED | FILLED | REJECTED | UNKNOWN`
- `ACKNOWLEDGED -> PARTIALLY_FILLED | FILLED | CANCEL_PENDING | CANCELED | EXPIRED | UNKNOWN`
- `PARTIALLY_FILLED -> PARTIALLY_FILLED | FILLED | CANCEL_PENDING | CANCELED | EXPIRED | UNKNOWN`
- `CANCEL_PENDING -> CANCELED | PARTIALLY_FILLED | FILLED | ACKNOWLEDGED | UNKNOWN`
- `UNKNOWN -> ACKNOWLEDGED | PARTIALLY_FILLED | FILLED | CANCELED | REJECTED | EXPIRED`
- 終端状態：`FILLED`, `CANCELED`, `REJECTED`, `EXPIRED`, `ERROR`

(3) GMOコインAPIステータスから内部11状態への変換規則（実装時公式スキーマ最終突合）
- `WAITING` / `ORDERED` & `executedSize == 0` -> `ACKNOWLEDGED`
- `WAITING` / `ORDERED` & `0 < executedSize < size` -> `PARTIALLY_FILLED`
- `CANCELLING` -> `CANCEL_PENDING`
- `EXECUTED` -> `FILLED`
- `CANCELED` -> `CANCELED`（`executedSize > 0` 時は部分約定分をポジション移行し残予約解放）
- `EXPIRED` -> `EXPIRED`（`executedSize > 0` 時は部分約定分をポジション移行し残予約解放）

8. Risk Gate・リスク予約・Emergency Reduction・実口座API禁止境界
========================================================================

- **Phase 1-A〜1-D（およびPhase 1全体）における実口座API・実注文の完全禁止**：
  Phase 1-A〜1-Dでは実口座APIへの接続、本番認証情報の読み込み、および実注文機能を完全に無効化・禁止する。実口座への接続・実注文機能は別フェーズ（フェーズ6の本番移行審査後、人間の明示的承認を得るまで）実装しない。
- **Emergency Reduction Executorの適用範囲**：
  通常Risk Gate停止時は、独立した「事前承認済みの決定論的Emergency Policyモジュール」が `EmergencyReductionAuthorization`（1回限り消費・有効期限付）を発行する。ただし**Phase 1〜2ではPaper環境／模擬口座アダプタ内での模擬実装に限定**する。
- **損失上限の計算定義**（数値候補：1トレード0.1〜0.25%、日次-1.0%、週次-2.5%、DD -5%警告/-8%停止、3連敗は未承認・仮定値）：
  日次リセットUTC 00:00、週次リセット月曜UTC 00:00。入出金・振替はDD（HWM基準）から厳密分離する。
- **DB競合制御**：SQLiteは `BEGIN IMMEDIATE`、PostgreSQLは `SERIALIZABLE` または行ロック（`SELECT ... FOR UPDATE`）＋楽観ロック用バージョン番号＋一意制約 `UNIQUE(account_id, instrument, client_order_id)`。

9. 実装基盤・データ契約（11種）・Event LedgerとProjection
